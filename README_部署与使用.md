# Reader Studio｜《Use AI to Direct AI》读者拓展工作台

版本：1.3.2　更新日期：2026-09-25

这是一个可以部署到 Debian 服务器的独立网页系统，不依赖本 ChatGPT 对话保持打开。用途是为 Huashan Chen 的英文书寻找合适的成年读者，发出阅读邀请、接收回复并推荐相关章节。书籍固定为 `Use AI to Direct AI`，ASIN `B0HK4KMQF4`。

**默认不发信、不搜索、不自动回复。** 首次部署产生独立随机管理员密码。你在网页里配置自己的服务，测试并明确启用后才开始工作。代码中不含真实邮箱密码、模型密钥或默认管理员密码。公开仓库的 `resources/history.json` 为空；私有历史导入必须由管理员单独提供和保管。

## 1. 已实现的功能

- 自动网页研究：每10轮按6/3/1搜索科技及AI实践者、参与儿童AI学习的成人教育者、相邻业务/创作实践者。画像匹配与联系资格分别记录；高相关但证据或许可不足的候选保留待办，不进入发信队列。研究阶段保存有来源指纹的原文快照。邮箱须逐字出现在HTTPS官方来源；经核实的学校/雇主人员页可用于确认身份和现任关系，不要求个人主页与机构邮箱同域。MX、禁止推销/采集、专用角色邮箱、来源身份、地点歧义及许可检查继续生效。找不到就不编造、不凑数。
- 启用研究后，Worker 每次挑一位待核候选，让审核任务 Profile 从新抓取的官方网页提议匹配与地点摘录，再由现有程序校验器核对原文及联系资格。单人失败后至少7天才自动重试，全局每5分钟至多排一位，仍受模型和抓取预算约束。模型不创建许可。升级暂缓、尚未尝试发送的 AI 首信可自动重新审核一次；其他人工处理事项仍由管理员处理。
- 自动首封邮件：研究先保存有指纹的官方来源原文快照；分阶段模型调用提取可追溯证据简报，再完整撰写主题和正文。独立审核检查实际全文与原文、书籍事实和邀请承诺，程序执行硬校验；低分或审核拒绝最多定向改写一次，仍失败则暂缓人工处理。首封正文保留主标题与 Amazon 出版事实，最多120个英文词且不含任何链接。完整副标题和固定引文模板均非必需。
- 持久限频：默认每日最多10封首封，前后间隔至少70分钟；配置不能超过10封/日或降到61分钟以下。**新安装默认 `America/New_York`、08:30—19:30**；70分钟间隔理论可容纳10封，实际运行可能更少，不承诺每日达额。旧数据库保留原时区和窗口；需要切换时，在配置中心明确点击“应用美东预设并暂停”。IANA时区自动处理夏令时，不使用固定香港时间换算；这也是统一美东窗口，不是每位收件人的本地时段。重启不清零，不积累欠额，不补发成批邮件。
- SMTP发信：SSL/TLS或STARTTLS，不降级明文；保存完整邮件内容与实际提交的MIME，可在后台下载 `.eml`。
- IMAP收信：单封最多512KB、最多100个MIME部分；超限邮件留在邮箱并记日志，进入“收信缺口待核查”并阻止后续外发；每次最多处理50封，积压清完前不继续发送。只读、`BODY.PEEK[]`、持续UID去重；每60分钟收取一次新增邮件，不会标记已读。手动收信任务和重启共用持久化小时门槛，失败后也按小时重试。首次同步从当前收件箱末尾开始，不扫描并自动回复全部历史。
- 来信三种处理：明确拒绝邀请（如“Nope”）直接停止联系且不回复；普通兴趣/问题/阅读进度/反馈由回复任务 Profile 撰写并独立审核；未知身份、验证不足、敏感请求、意图不明、审核失败或超出轮次交人工。先分离引用，“No, I don't have Kindle Unlimited”不能只凭no判作拒绝。收件列表和详情显示处理结果；拒绝保留停发记录。生产分类、回复和审核按作者授权使用已配置的 Sonnet Profile。
- 持续自动运行：配置开启后跨重启保存，来信分阶段任务优先于研究，不会因单封人工事项停止其他任务。收信临时故障阻止外发，恢复健康后继续；schema升级仍须核查后恢复开关。详见 [持续运行与来信处理](docs/CONTINUOUS_REPLY_TRIAGE.md)。
- 退订、明确拒绝、匹配原发送记录的永久退信进入停发名单；不继续自动回复，也不发“确认退订”邮件。
- 后台：总览、候选资料、完整往来、发件/收件筛选、按日期区间统计、CSV和STATUS.md导出、配置中心、操作日志、待人工处理。
- 历史迁移：附带你在对话中实际确认发送过的12位联系人，导入后不会重复发首封。只记录原对话确认的事件，不冒充原始邮件内容、SMTP发送或新读者数据。这12人的历史线程没有原Message-ID，新的回信首次需要人工接手；通过本系统回复并建立新线程后才可自动处理。

每天10封是上限，不是必须完成的数量。若来源/许可不足、模型预算用完、邮箱故障或窗口不足，当天可能少于10封。

### 1.1 本次新增的运行保护

- 相同邮箱全历史去重；匿名后保留抑制哈希，研究阶段就跳过，不重新采集身份。
- 相同业务域名及其父/子域默认365天内不重复首封；待审/排队任务也占位。公共邮箱域如gmail不作为一个企业去连带封锁，但仍需真实许可。不同域名下同一家公司、共享托管平台和复杂公共后缀不作自动组织归属推断。
- MX只证明域名发布了邮件交换记录，不证明具体邮箱存在或愿意收信。无MX、Null MX、NXDOMAIN、DNS错误/超时会挡住自动陌生邀请；无MX并不在技术上必然等于邮箱不存在。
- 近24小时两个不同地址硬退信、一次已关联投诉，或近7天已联系样本中至少3人退订/拒绝且占比达到30%，会熔断。阈值是本系统保守策略，不是Gmail官方阈值。
- 支持可关联的DSN、ARF以及管理员实际在提供方后台核实的投诉。不能读取所有垃圾箱点击或所有投诉率。解除熔断需写处理依据；不恢复被退订的人，也不自动启动发送。
- SMTP 5.7.x/内容/认证策略拒绝不误判为收件邮箱不存在；明确拒绝、临时拒绝与无法确定是否接受分开保存。
- 外出/自动通知不算人类回复；转发EML或附件里的文字不拿来识别读者行为或执行指令。

**已经部署1.0或1.1：不要覆盖.env或数据卷。先看 `docs/升级与回退_v1.2.md`，使用 `deploy/upgrade.sh`。迁移至schema3后暂停全部自动化，保留原时区、窗口、密钥、UID及历史；旧待发邮件转held。公开候选须重新取得v3来源验证，历史已联系者不能借此重新发首封。**

## 2. 推荐部署：Docker Compose（优先）

推荐至少2GB内存，剩余磁盘5GB以上。模型和搜索在你配置的外部API上运行，本机不部署大模型。1.2是单台服务器、单管理员、单邮箱、单Worker；SQLite必须放本机磁盘，不放NFS或多副本共享网络盘。

### 2.1 前置检查

在Debian服务器终端确认：

```bash
docker --version
docker compose version
docker info
```

尚未安装时，按Docker官方Debian安装文档完成：
https://docs.docker.com/engine/install/debian/

安装脚本不会擅自执行apt、覆盖现有Nginx、占用80/443或修改其他业务服务。

### 2.2 上传、解压、启动

把交付ZIP上传到服务器，例如 `/opt/`，然后：

```bash
cd /opt
unzip Book_Reader_Outreach_v1.2.zip
cd Book_Reader_Outreach_v1.2
bash deploy/setup.sh
```

第一次构建需要访问Python镜像仓库和PyPI。终端会显示管理员 `admin` 和一段随机密码，立即存入密码管理器。重复执行初始化不会覆盖已有管理员密码。

该脚本会导入12条历史已联系记录，启动 `web` 和 `worker`，**不会启用任何外发**。不需要这份历史时，可不用setup.sh，改为先 `docker compose build`，然后运行 `docker compose run --rm --no-deps web python -m outreach.cli init`，最后 `docker compose up -d`。

### 2.3 不需要域名也能管理：SSH隧道

系统默认只绑定服务器 `127.0.0.1:8096`。在你的Mac另开终端，替换实际SSH用户名和服务器IP：

```bash
ssh -N -L 8096:127.0.0.1:8096 用户名@服务器IP
```

保持终端运行，然后Mac浏览器打开：

```text
http://127.0.0.1:8096
```

该模式下HTTP流量经过加密SSH隧道，`.env` 保持 `OUTREACH_SECURE_COOKIE=false`。**不要直接把8096开放到公网，也不要把Compose端口绑定改为0.0.0.0。**

没有公网域名时，邮件提供“回复STOP”退订；HTTPS一键退订不是启用的前提。

### 2.4 已有域名时

使用独立子域名并复用你已有的可信HTTPS反向代理。示例见 `deploy/nginx-http.example.conf`；这是HTTP引导配置，不是已经带证书的生产HTTPS配置。你需提供真实域名与证书，完成HTTP→HTTPS重定向。

HTTPS启用后：
1. `.env` 改 `OUTREACH_SECURE_COOKIE=true`。
2. `docker compose up -d --force-recreate`。
3. 网页“公网地址”填本系统实际可访问的HTTPS域名根路径（例如你自己的推广后台域名，不是书籍资源站）。
4. 先验证 `/u/<token>` 的退订功能。系统GET只展示确认，POST才停发，避免链接扫描器误退订。

未完成HTTPS前继续用SSH隧道即可。默认不启用访问日志，避免把退订令牌写入普通Web日志。

## 3. 网页配置：只需要你掌握的服务信息

进入“配置中心”：

| 区域 | 填写什么 | 注意 |
|---|---|---|
| 发件身份 | Huashan Chen、实际发件邮箱、真实邮寄地址 | 地址会出现在每封邮件底部，不能写虚构地址。可使用有权使用的企业邮寄地址。 |
| SMTP | 主机、465+SSL或587+STARTTLS、用户名、应用密码 | 发送者地址必须是该账户有权使用的地址。服务商必须允许此用途。 |
| IMAP | 主机、993+SSL或143+STARTTLS、用户名、应用密码、INBOX | 1.2支持IMAP用户名/应用密码，不支持POP3或OAuth交互登录。服务商须开启IMAP。 |
| 模型 | API Base URL、API Key、模型名 | 填写实际供应商的HTTPS地址和协议；模型名可先填原定的`gpt-6-luna`。该字符串不是型号可用性证明，实际权限/额度以你的API账号为准。 |
| 搜索 | 内置web_search或Brave | 模型的普通聊天接口不等于拥有联网搜索。 |
| 调度 | 时区、发送窗口、默认70分钟、每日10封 | 运行的是“最多10封”，不是保证每天找到/发出10封。 |
| 凭证 | 在网页填写 | 保存后不回显，留空保留已有值；不要把密码发到聊天或源码里。 |

密码在SQLite中以Fernet加密，解密主密钥单独保存在数据卷 `master.key`。这能减少误导出配置时的暴露，但不是整台服务器失陷后的保护；备份含主密钥，必须私密保管。

### 3.1 模型协议与搜索怎么选

**原生路径：Responses + native web_search。** 后台会要求实际返回web_search调用记录和来源，再自行读取来源网页验证邮箱，而不是拿模型记忆当来源。

**Anthropic原生路径：Messages + native。** 使用基础 `web_search_20250305`，检查真实 `server_tool_use` 与对应结果；HTTP200中的工具错误会失败，不作为研究成功。每轮总计最多4次搜索、最多2次pause_turn续接，原始assistant content（含encrypted_content）完整传回；每次HTTP请求计入模型预算。未启用动态过滤或本地代码执行。实际模型/账号/网关必须支持该工具，否则选择Brave，不按模型名称推断权限。

**兼容网关路径：Chat/Responses/Anthropic Messages + Brave。** 第三方只提供聊天而未实现web_search时，在网页切换搜索方式为Brave，并填写自己的Brave API Key。系统通过Brave找页面后，从最多6个落地页各沿最多2个实际出现的同站HTTPS Contact/About/Team链接继续读取，再交给模型提取。没有发现链接就不猜路径，不跨站扩爬、不递归整站，不绕过robots/禁止联系声明；来源读取仍受每日预算。之后Researcher独立核验确切邮箱页和活动页，搜索摘要不能替代证据。

研究/写信模型和分类模型可在同一端点分别填写；未填分类模型则沿用主模型。Responses、Chat Completions和Anthropic Messages按不同协议组包，模型名称不硬编码。兼容网关不支持reasoning参数时关闭“发送reasoning参数”；Anthropic不发送该参数。不保证某个具体型号已在你的账号可用，也不依据模型名字推测它有联网工具。

1.2支持公共HTTPS 443接口；不支持浏览器Cookie登录、Codex CLI套壳、任意脚本工具或内网地址。模型、搜索、SMTP和IMAP都需要你自己的真实服务。模型和搜索的API调用可能独立计费；程序不依赖你浏览器上的ChatGPT会话。

### 3.2 可信回信验证

自动回复默认要求接收服务器的 `Authentication-Results` 显示DMARC通过，并与From域名对齐。填入自己收件提供方实际使用、且保证会清除外部伪造同名验证头的 `authserv-id`；`mx.google.com` 只是Gmail的常见示例，**其他邮箱不能照抄**。

不知道应填什么时，先从真实收到的一封测试邮件“显示原文”检查，必要时向收件服务商确认。若提供方不提供可信验证头，默认转人工比降低验证可靠；网页可关闭该门槛，但会减弱防伪造能力，必须由管理员决定。即使关闭，系统仍要求相同联系人、引用本系统已发Message-ID、Reply-To不变；它们不是DMARC的等价替代。

### 3.3 合法联系范围

默认 `仅已记录许可`：研究可以找候选，只有你记录了真实联系许可的人可以自动发首封。

需要无人值守找到并邀请新候选时，管理员可选择 `已核实美国公开业务资料` 并确认用途：程序还会核对官方业务站点、邮箱原文、姓名、活动原文、美国所在地与禁止推销声明。个人邮箱、未知地区、国外个人/独资经营者、无来源、来源不匹配等只进入待核实，不自动放行。

所在地证据接受 `Based in Austin, Texas`、`Located in Brooklyn, NY`、`Portland, OR 97201` 和明确的US-based语句。摘录必须出现在实际读取的单一页面；客户、曾居地、会议地点、否定或国外冲突上下文不放行；Chicago-based这类城市名本身不够。城市+州解析不是完整地名数据库，不保证实际住址/身份或适用法，只提供可审阅的来源信号。页面展示所用规则和失败理由。

这不是“美国地址=法律自动批准”。真实公共业务资料也不必然等于许可；适用法、个人数据处理、提供方条款和退订由账号责任人核实。不同地区要求不同，不建议首版全球无差别冷发。

研究目标轮换覆盖美国、英国、德国、法国、西班牙、意大利、荷兰、日本、巴西、加拿大、墨西哥、澳大利亚和印度。英国在数据库中用 `GB` 表示。非美国公开业务资料可进入候选库，但不会仅凭上架国家或公开邮箱自动外发；另有已记录联系许可时，才可走许可联系人路径。

选择 `邮件生成后的处理 → ai_review` 时，首封及自动回复先由模型独立审核文案；只有明确通过、正文未改变且程序再次核对来源与发信条件，才允许发送。回复另须通过真实线程、身份验证和退订检查。模型拒绝或审核出错会保留邮件，不会自动发送。`review` 在 AI 与程序检查后还需人工批准；`automatic` 兼容模式同样必须通过独立 AI 审核和程序硬校验。

### 3.4 版本 1.3.1 的研究、文案与人工处理

`research_countries` 使用目标国家代码列表，默认仅 `US`；启用多个国家后按所选顺序轮换。非美国公开资料仍须单独记录联系许可。候选页可二次确认并归档当前范围外的待核候选；原记录、去重和停发名单保留。`python -m outreach.cli qualification-report` 只输出资格、原因、国家与当日用量的汇总，不输出姓名、地址或来源原文。

`quality_min_each` 默认 2（0–4），`quality_min_mean` 默认 3.0（0–4.5）。审核四个分数均为越高越好，`reply_burden=5` 表示读者回复最省力。旧版已保存的低分批准也会失效。`ku_enrolled_until` 默认 `2026-12-15`，空值表示未加入 KU；系统按配置时区判断日期。到期当天书籍事实版本变化，未发草稿会暂缓，须重新生成或审核；过期后文案不得提及 Kindle Unlimited 或 KU。

来信页面可二次确认“人工接管回复”。原 AI 草稿和审核记录保留为 `superseded`；人工正文仍禁止附件和非固定 Amazon 图书链接。退订、旧来信、已尝试发送或 SMTP 状态不确定的回复不能通过接管重做。自动回复的分类、撰写、审核各占一个 Worker 周期，新来信到达会使旧任务停止。

自动研究间隔可在配置中心调整，默认240分钟。美国公开业务联系范围下，研究交替覆盖美国与其他目标国家，避免只累积暂不能自动外发的候选。自动回复开关与首封发送独立；可信收件验证服务器未配置时，回复仍被身份检查拦截，但不阻止首封发送。

### 3.5 正式启用顺序

1. 保存配置（仍暂停）。
2. 点击“测试SMTP”“测试IMAP”“测试模型”。在“任务与日志”查看结果。SMTP测试只认证，不证明投递成功；模型测试会产生一次请求。部分SMTP服务不会自动把外发邮件写入“已发送”文件夹，本系统MIME记录和服务商日志是独立证据。
3. 新装点击“收取新邮件”，建立IMAP游标；每小时门槛对手动和自动相同，不高频强刷。
4. 使用你控制且同意测试的另一邮箱，完成 `docs/上线前真实服务验收.md` 的一次首封→回信→回复→退订闭环。
5. 点击“研究一批候选”，查看邮箱来源、匹配理由与待核实原因。
6. 升级用户先核对是否需要“应用美东预设并暂停”；新装已用美东窗口。确认模式与地域范围后，在首页启用“自动研究”及“发送/受限自动回复”。

首次联调前不要直接对真实陌生人试发。没有真实密码/API Key，本包没有替你进行任何外部发送。

## 4. 日常怎样用

**总览**：当天首封、来信、已回复、需要人工处理；Worker心跳和收信健康。收信超过75分钟未成功、最近一次收信失败、仍有积压或人工待核查缺口时，都会暂停实际外发。每小时才收一次邮件意味着通过邮件发送的退订可能要到下一轮才处理；已经入库的抑制立即拦截，公网网页退订不等待IMAP。

**候选读者**：v1.2会展示所在地解析规则与核验理由；不通过可查看原文或重新核验，不需要伪造邮编。按状态、姓名/邮箱、是否已回信筛选。点联系人看介绍、匹配理由、邮箱来源链接、原文片段、来源指纹和完整往来。研究来源未经核实会明确标注，不等于已联系。

**发送与队列**：按日期、首封/自动回复/人工回复、状态查询。`queued`不等于已发；`accepted`只是SMTP已接受。新首封详情可展开“首封个性化依据”查看实际引用、主题词和模板选择。未尝试发送的draft/held邮件可以修改主题和正文，保存后回到待审，重新批准才排队。发送过或提交不确定的邮件不能被编辑成仿佛未发送。`rejected`与`deferred`是明确拒绝，`uncertain`是结果不确定；全部禁止自动重发。发件详情可以下载实际提交的 `.eml`，正文包含发送当时的身份/退订页脚，后续改配置不会改历史内容。

**回信与处理**：按日期、是否已经回复、分类（兴趣/问题/反馈/退订/自动通知等）和处理状态过滤；同一页面显示来信及关联回复。陌生发件人、伪造/无法验证、Reply-To换地址、历史线程未建立关联、需要付费/版权/附件等不会自动回复。已确认联系人可人工接手；系统仍限频，不改变收件人。

**自动回复默认**：每日最多20封回复，每5分钟最多1封；每位联系人滚动24小时最多2次自动回复，自动回复总计默认最多2次，超出转人工。仅响应新的真实来信，没有首封未回复自动催促机制，不会自动回复自己的邮件、退信、邮件列表、自动度假回复。

**统计与导出**：起止日期均包含在内，来信时间是本系统读取并入库的时间（非发件人可改的Date头）；按配置时区查询首封、回信、已回复和每日明细及折线图；增加退信、已观测投诉、退订/拒绝与本期邀请批次回复率。批次回复率是本期收到SMTP接受的受邀联系人中，截至查询时已有回信的比例，不是随便拿两个不同人群的日计数相除。导出的CSV包含个人资料，勿上传公开网站。兴趣/阅读/练习/反馈必须依据来信文字记录；书籍订单、KENP、邮件打开率、Amazon评论没有接入，不能从发信或点击推算。

**状态文件**：Worker约每小时更新数据目录的 `STATUS.md`，也可以网页立即导出。这是服务器本地文件，**不会自动同步到其他ChatGPT分支或Library**；把导出的状态交给总控即可。

## 5. 运维命令

```bash
cd /opt/Book_Reader_Outreach_v1.2
docker compose ps
docker compose logs --tail=100 web worker
# 紧急停止后续研究、发送、回复（保留数据）
docker compose exec -T web python -m outreach.cli pause
# 忘记管理员密码：重置为随机密码，并使旧会话失效
docker compose exec -T web python -m outreach.cli reset-password
# 查看当前真实状态
docker compose exec -T web python -m outreach.cli status
# 私有备份（含敏感资料和解密密钥）
bash deploy/backup.sh
# 停止服务但保留数据
docker compose down
```

不要执行 `docker compose down -v`，它会删除数据卷。已经提交到SMTP的单封邮件无法通过“暂停”撤回。容器重启后调度继续读取原数据库额度，而不是从0重新发。

### 5.1 SMTP超时的处理

SMTP与本地数据库不能做跨系统原子提交。出现“服务器可能已接受，但本机没得到最终结果”时，记录标为 `uncertain`，**不自动重发**。先查发件服务日志；有证据已接受时在详情按真实时间确认，否则取消并人工处理。不要删除数据库记录来“重新试一次”。

### 5.2 小时收信和熔断处理

收信任务按“距上次尝试至少60分钟”调度，不是强制整点。Worker每30秒只进行本地状态检查，网页数字刷新也只查询本地数据库；不会因此每30秒/2分钟去连IMAP。明确手动连接测试不算同步，不读取邮件。

若某次收信失败，外发当即被健康门槛拦住，到下次整小时尝试成功、且无其他问题才继续；不高频重连。若UIDVALIDITY变化、超大邮件或解析失败造成缺口，后台总览会显示待核查UID。你需在邮箱实际查看并处理退订/投诉后，填写证据确认缺口已处理。不要只为了恢复发送清掉提示。

熔断除了发送被关闭，还会在总览显示原因。实际查清原因、处理停发人后，记录解除依据；然后才手动再启用发送。不明SMTP结果仍需逐条核对，不会因解除熔断批量重发。

### 5.3 从备份恢复

恢复必须在没有正在运行的旧Worker的情况下执行，并核对备份时刻以后实际发出的邮件，避免旧备份回滚导致重复联系。建议恢复到**新的空卷/新目录**，保留旧数据。

原生模式恢复示例：

```bash
# 停止两个服务后，选择一个全新的空目录
OUTREACH_DATA_DIR=/var/lib/book-reader-outreach-restored \
  /opt/book-reader-outreach/.venv/bin/python -m outreach.cli restore --input /安全位置/outreach-backup.zip
```

Compose迁移时，可创建临时服务，把新空命名卷挂载 `/data`，把本地备份目录只读挂 `/backup`，执行：

```bash
# 替换 /绝对备份目录 和 实际备份文件名；以下创建新卷，不覆盖旧卷。
docker volume create book-reader-restored
docker run --rm --user 0:0 --entrypoint sh -v book-reader-restored:/data \
  book-reader-outreach:1.2.0 -c 'chown 10001:10001 /data && chmod 700 /data'
docker run --rm -v book-reader-restored:/data -v /绝对备份目录:/backup:ro \
  book-reader-outreach:1.2.0 python -m outreach.cli restore --input /backup/实际备份文件名.zip
```

恢复后需要在Compose的数据卷定义中显式使用该新卷，然后先只启动web核对，之后再启动worker。所有发送/研究/回复开关自动关闭，旧排队邮件转待处理，连接验证失效，管理员会话失效。重新启用之前处理备份之后的历史差额；不要让新旧服务器同时运行Worker。

## 6. 没有Docker时：原生systemd

推荐仍用Compose；原生示例见 `docs/原生Debian部署.md`。两种方式**二选一**，不要让两个Worker对同一数据目录运行。
