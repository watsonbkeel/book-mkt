# 扩展到其他推广领域

本项目可复用的是“有证据的潜在客户 → 模型完整写信 → 独立审核 → 程序校验 → 受控发送 → 来信处理”的结构。当前产品知识和部分规则仍固定于一本书，以下是扩展路径，不是已经实现的通用活动功能。

## 1. 哪些可以直接配置

可在后台修改邮箱、发件身份资料、模型 Profile/任务路由、推理参数、研究国家列表、研究周期、预算、2000人候选池目标、窗口和已有范围内的邮件限额。

这些设置**不能**直接把图书推广变成任意产品推广。`sender_name` 改成另一人不会自动替换代码中的作者、书名、章节、Amazon 链接或页脚。“研究国家”也不是联系许可开关。

## 2. 迁移到一个新领域时要修改的模块

| 内容 | 当前实际来源 | 新领域要提供什么 |
|---|---|---|
| 权威产品事实 | `outreach/domain.py` 的标题、作者、URL、CHAPTERS；`contracts.py` 的 BOOK_FACTS、AUTHOR_POSITIONING、版本及 KU 日期 | 经业务方批准的名称、主体、已上线能力、限制、可信 URL、可用资料目录；删除不适用的 KU/Amazon 假设 |
| 谁值得研究 | `outreach/ai.py` 的 discover 查询、target_country；`research.py` 的6/3/1画像轮换；`domain.py` 的 PERSONAS；`qualification.py` 与官网核验 | 成年目标受众、活动/职业相关性、官方来源与联系资格。新画像必须与枚举、统计、UI同步，不能仅换一个搜索词 |
| 收件人价值 | `ai.py` 的 brief、initial_copy、_review、reply_copy | 事实与应用设想分开、一个具体价值、一个可兑现邀请；不要虚构客户痛点、关系或案例 |
| 首信承诺和交付 | `generation.py`、`pipeline.py`、assets 表 | 能先生成、审核、保存的演示/摘要，回复兑现同一资产；产品资料不足时交人工 |
| 硬校验与版本绑定 | `contracts.py`、`domain.py`、`generation.py` | 新的允许事实/链接/承诺，确保文案和审核版本一致；仅修改提示词不能绕过程序约束 |
| 身份与邮件呈现 | `mail.py`、`composition.py` 的兼容路径、templates | 真实主体、准确身份、地址、披露与退订方式；清理旧书名和章节残留，不能只改网页标题 |
| 收件处理和统计 | `ai.py` classify、`triage.py`、`engine.py`、`reports.py`、网页模板 | 保留停止联系/自动回复/人工三条路径；将阅读/练习等指标改为该领域可由文字证实的事件 |
| 兼容与验证 | `settings.py`、迁移脚本、tests、预览工具、文档 | 新设置走 DEFAULTS/RANGES，schema变更安全迁移且暂停自动化；合成数据覆盖所有新分支 |

现有 book/policy/positioning/prompt 版本和证据、Profile、正文共同绑定审核。改知识或提示词后，旧未发稿需重写或复审；已发送历史保持原文。新领域不能把原书已审核资产当作自己的已授权内容。

## 3. 推荐实施顺序

1. 写一页业务规格：推广主体、受众、允许陈述、禁止承诺、交付材料、固定链接、有效日期及需人工处理的情形。
2. 建立新分支，使用空的临时数据库和合成成年联系人；先复用 Engine/Worker/分阶段任务，避免另建一套平行发送系统。
3. 统一知识来源，让简报、写作、审核、资产和回复使用同一版本。先跑错误案例：不存在的功能、收益保证、错误链接、无法兑现的邀请、无来源陈述。
4. 更新研究画像与资格证据。适合推广不等于允许联系，保留来源、许可/地区、去重、停发等独立门槛。
5. 在应用实际入口生成不同受众的首信与完整来回预览。mock验证流程；授权后的真实模型预览再检查语义、成本和网关能力。没有真实调用就标MOCK_ONLY。
6. 业务方审阅预览，批准绑定具体代码、内容版本和文件哈希；再单独确认部署与自动运行。
7. 在独立部署中用自有、同意测试的邮箱验证线程、退订与异常。备份并准备回退后，小规模启用。

## 4. 可探索的用例（尚未实现）

| 领域 | 可核实的受众关联 | 可兑现的轻量邀请 | 需要替换的本书逻辑 |
|---|---|---|---|
| 另一书籍/课程 | 成年教师、专业读者的公开课程或作品 | 已审核的原创练习示例或课程资料摘要 | 书籍事实、章节、阅读入口、授权与获取方式 |
| 软件或工具 | 官方页面描述的业务流程或工具需求 | 已审核的演示步骤或场景示例 | 图书标题/章节校验，软件功能与版本证据 |
| 专业服务 | 官方团队的业务范围，与真实可提供服务的关联 | 范围明确的问题讨论或已有服务说明 | 服务能力、交付边界、身份和人工承诺审批 |

这些只是未来设计方向，不是对任何真实收件人需求的判断。

## 5. 多活动与扩大规模

当前没有 campaign_id、租户隔离、多邮箱调度或通用活动管理界面。最快的受控试点是在**独立 Compose 项目、数据卷、发件身份和授权范围**中运行一个经修改的单活动版本；不要两套 Worker 共用数据库。原部署脚本假定默认 Compose 项目名，修改后必须人工核对端口、卷、备份路径和升级步骤。

正式多活动能力需先设计活动事实版本、任务归属、预算、审计和隔离；同时保留适当的跨活动停发/去重策略，不能让拒绝者因为换活动又收到邮件。凭证不得进入模型上下文或公开仓库。

每日发信上限当前硬限制10，最短间隔61分钟。扩大候选池不修改这些限制。未来提高发送能力应单独审阅：服务商额度、联系授权、退订处理容量、发送窗口能容纳的数量、失败/投诉控制、并发与SMTP幂等边界。不能只提高一个数据库数字，也不能靠换域名或多部署规避停发记录。尚未对高吞吐发送作生产验收。
